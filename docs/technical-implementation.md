# MCM Showcase 기술 구현

## 1. 프로젝트 개요

MCM Showcase는 오프라인 매장에서 수집한 고객 행동을 바탕으로 상품을 추천하고, AR 피팅과 AI 아바타 이미지를 통해 개인화된 스타일 경험을 제공하는 서비스입니다.

고객의 매장 층별·카테고리별 체류 시간, 회원 위시리스트, AR 피팅 중 발생한 상품 선택 이력을 하나의 세션으로 연결합니다. 수집된 정보는 Python 추천 서버에 전달되며, 추천 이후의 행동도 다시 개인화에 반영됩니다. 체험 종료 후에는 완성된 코디와 피팅 기록을 My Closet에서 확인할 수 있습니다.

> 매장 방문 및 행동 수집 → AR 세션 연결 → 초기 추천 → AR 피팅 및 반응 수집 → 추천 갱신 → AI Avatar Look 생성 → My Closet 저장

## 3. 시스템 구조

```text
[Client / AR Display]
          │ REST API
          ▼
[Spring Boot Backend] ───── [MySQL]
          │                   ├─ 방문 및 체류 이력
          │                   ├─ AR 상호작용
          │                   ├─ 회원 및 위시리스트
          │                   └─ Style Profile / Today Look
          │
          ├─ [Python Recommendation Server]
          │      ├─ 초기 선호도 구성
          │      ├─ 상품 및 코디 추천
          │      └─ 이미지 배경 제거
          │
          └─ [FLUX API]
                 └─ 아바타와 상품 기반 착장 이미지 생성
```

Spring Boot 서버는 클라이언트, DB, 외부 AI 서버 사이의 오케스트레이터 역할을 합니다. 외부 서버의 결과를 그대로 사용하지 않고 내부 상품 데이터와 대조하고 세션 상태를 검증한 뒤 서비스 응답으로 변환합니다.

### 백엔드 계층 구조

패키지는 `Controller → Service → Repository → Entity` 구조로 분리했습니다.

- Controller: HTTP 요청 수신, 입력 검증, 응답 DTO 반환
- Service: 세션 상태 검증, 데이터 가공, 트랜잭션 및 외부 API 흐름 제어
- Repository: Spring Data JPA 기반 조회·저장과 정렬·존재 여부 쿼리
- Entity: 연관관계와 세션 종료·회원 연결 등 상태 변경 규칙 보유
- Client: Python 서버와 FLUX API 통신 책임 분리
- DTO: 클라이언트 API 모델과 외부 서버 통신 모델 분리

엔티티를 응답으로 직접 노출하지 않고 record 기반 DTO로 변환합니다. 지연 로딩 객체가 직렬화되는 문제를 피하고 DB 모델과 API 계약의 결합도를 낮췄습니다. 주요 연관관계에는 `FetchType.LAZY`를 적용하고 필요한 데이터는 서비스 트랜잭션 안에서만 접근합니다.

엔티티는 정적 팩토리 메서드로 생성하며, 세션 종료나 회원 연결은 엔티티 메서드로 캡슐화했습니다. 예를 들어 `ArSession.end()`는 중복 종료와 잘못된 종료 시각을 엔티티 내부에서도 검사합니다. Service의 HTTP 수준 검증과 Entity의 도메인 검증을 함께 적용하여 다른 코드 경로에서도 기본 규칙이 유지됩니다.

### 세션 중심 데이터 연결

```text
CustomerSession ──┐
                  ├── ArSession ── ArInteraction ── Product
Member ───────────┘       │
                          └── StyleProfile ── TodayLook ── TodayLookItem
```

`arSessionId`를 중심으로 방문 정보, 회원, 성별, 피팅 행동, 최종 스타일 결과를 연결합니다. 방문 세션과 회원은 선택 관계이므로 회원·비회원 흐름을 하나의 모델로 처리하며, 체험 도중 또는 종료 후 회원을 연결해 기존 결과를 귀속시킬 수 있습니다.

## 4. 주요 기능 구현

### 4.1 방문 세션 및 매장 체류 데이터 수집

비회원도 체험할 수 있도록 익명 `CustomerSession`을 생성합니다. 시작·종료 시각과 `ACTIVE`, `COMPLETED` 상태를 저장해 방문 단위 생명주기를 관리합니다.

고객이 특정 층과 상품 카테고리에 머문 기록은 `ZoneInteraction`으로 저장합니다. 입장·퇴장 시각을 검증한 뒤 체류 시간을 초 단위로 계산하고, 실제로 존재하는 `StoreZone`과 `Category` 조합만 허용합니다.

추천 서버에 전달할 때는 동일한 층·카테고리의 체류 시간을 합산합니다. 단순 방문 여부보다 어느 공간과 상품군에 더 오래 관심을 보였는지를 초기 선호도로 활용합니다.

주요 검증 사항은 다음과 같습니다.

- 퇴장 시각이 입장 시각보다 빠른 요청 차단
- 존재하지 않는 층, 카테고리 및 조합 차단
- 종료된 방문 세션의 중복 종료 차단
- 지원 범위를 초과한 체류 시간 차단

### 4.2 AR 세션 통합 관리

`ArSession`은 방문 정보, 회원, 성별, AR 피팅 이력을 연결하는 중심 엔티티입니다. AR 기기에서 익명 세션을 먼저 생성한 뒤 방문 세션과 회원을 단계적으로 연결할 수 있습니다.

- 방문 세션 연결: 오프라인 체류 이력을 추천 입력으로 사용
- 회원 연결: 기존 위시리스트와 회원 성별을 개인화에 사용
- 성별 설정: 비회원에게도 성별 기반 추천 제공
- 세션 종료: 종료 후 새로운 상호작용 등록 차단

회원 또는 방문 세션 연결 트랜잭션이 커밋된 뒤 추천 초기화를 실행합니다. `afterCommit`을 사용해 외부 API 호출이 DB 저장보다 먼저 실행되는 문제를 방지하고, 추천 서버 장애가 정상적인 세션 연결까지 롤백시키지 않도록 실패를 로그로 분리했습니다.

AR 디스플레이와 다른 클라이언트를 연결하기 위해 최근 1분 이내에 생성된 미연결 활성 AR 세션을 조회하는 기능도 제공합니다.

세션을 연결할 때는 대상 리소스 존재 여부와 방문 세션의 `ACTIVE` 상태를 먼저 검사합니다. 이미 다른 방문 세션이나 회원이 연결되어 있으면 `409 Conflict`를 반환하지만, 같은 대상을 다시 연결하는 요청은 허용해 멱등성을 확보했습니다. 회원에게 성별 정보가 있으면 AR 세션에도 자동 반영합니다.

### 4.3 행동 데이터 기반 상품 추천

추천은 초기 추천과 갱신 추천으로 구분합니다.

초기 선호도에는 다음 데이터가 사용됩니다.

- 층·카테고리별 누적 체류 시간
- 회원의 기존 위시리스트 상품
- 사용자의 성별과 요청 카테고리

카테고리별 Top-K 추천 개수는 기본 6개입니다. Python 서버가 반환한 상품 ID를 DB에서 다시 조회하여 실제 존재 여부와 카테고리 일치 여부를 검사합니다. 응답에서는 Python 서버의 추천 순서와 점수를 유지합니다.

갱신 추천에는 기존 선호도와 함께 AR 피팅 중 누적된 상품 선택 및 위시리스트 행동을 전달합니다. 이를 통해 첫 추천은 매장·회원 데이터를 사용하고, 후속 추천은 실시간 피팅 행동까지 반영하는 점진적 개인화를 구현했습니다.

Java 백엔드는 추천 알고리즘 자체보다 입력 데이터의 수집·정제와 결과 검증을 담당합니다. Python 내부 모델과 점수 계산은 별도 문서에서 다룹니다.

체류 데이터는 `(zone, category)`를 복합 키로 한 `LinkedHashMap`에 저장합니다. `Duration.between()`으로 체류 시간을 구하고 `merge()`로 동일 조합을 합산하여 최초 등장 순서를 유지합니다. 추천 결과는 `findAllById()`로 한 번에 조회한 후 ID Map으로 변환하고, 외부 응답 ID를 다시 순회해 순서를 복원합니다. JPA 조회 순서에 의존하지 않고 추천 순위와 점수를 그대로 유지하기 위한 처리입니다.

### 4.4 AR 피팅 및 위시리스트 동기화

상품 선택, 선택 해제, 위시리스트 추가·삭제 행동은 `ArInteraction`으로 순서대로 저장합니다. 세션별 `sequenceNo`를 증가시켜 사용자의 행동 흐름을 재구성할 수 있습니다.

회원이 연결된 세션에서는 AR 위시리스트 행동과 실제 `MemberWishlist`를 동기화합니다.

- `WISHLIST_ADD`: 중복 확인 후 저장
- `WISHLIST_REMOVE`: 회원-상품 매핑이 존재하면 삭제
- 비회원: AR 행동 이력만 저장

상품 선택 또는 해제 시 현재까지 유효한 선택 상품을 계산하여 피팅 이미지를 갱신하고, 생성된 이미지 URL을 응답에 포함합니다.

#### 피팅 상태 계산

현재 착장 상태를 별도 컬럼에 저장하지 않고, `sequenceNo` 순서로 전체 선택 이벤트를 재생해 계산합니다.

- `PRODUCT_SELECT`: 같은 카테고리의 현재 상품을 새 상품으로 교체
- `PRODUCT_DESELECT`: 현재 선택 상품과 ID가 같을 때만 해제
- BAG, TOP, BOTTOM: 사전 제작된 피팅 이미지 지원
- SHOES, ACCESSORIES: 행동은 저장하지만 피팅 이미지 응답에서는 제외

최종 상태에 따라 이미지 경로를 결정합니다.

```text
기본          fittings/{gender}/{gender}.png
가방          fittings/{gender}/bag-{productCode}.png
상의          fittings/{gender}/top-{productCode}.png
하의          fittings/{gender}/bottom-{productCode}.png
상의 + 하의   fittings/{gender}/top-{topCode}-bottom-{bottomCode}.png
```

계산된 경로를 이미지 루트 아래로 정규화하고 실제 파일이 존재할 때만 URL을 반환합니다. 준비되지 않은 조합은 잘못된 URL 대신 `null`을 반환합니다. 새 행동의 순번은 세션의 마지막 `sequenceNo + 1`로 생성하며 최초 행동은 1부터 시작합니다.

### 4.5 상황 기반 AR 메시지

피팅 이력을 분석하여 적절한 시점에 안내·추천 메시지를 노출합니다. 메시지는 피팅 횟수, 이전 노출 이력, 쿨다운을 함께 고려합니다.

주요 트리거는 첫 피팅 완료, 특정 존 관심 증가, 연관 카테고리 확장, 관심 카테고리 전환입니다. 메시지 이력은 `ArMessageHistory`에 저장하여 반복 노출을 방지하며 한국어와 영어를 지원합니다. 평가 시 AR 세션을 비관적 락으로 조회해 동시 요청에 의한 중복 메시지 생성을 줄였습니다.

메시지 평가에는 이미지 파일이 실제로 존재하는 피팅 이벤트만 사용합니다. 선택 기록이 있더라도 지원하지 않는 카테고리이거나 조합 이미지가 없으면 피팅 횟수에서 제외하여, 화면에 결과가 표시되지 않았는데 메시지만 발생하는 상황을 방지했습니다.

### 4.6 Avatar Look 저장 및 이미지 생성 연동

AR 체험 결과를 완성된 스타일로 저장하기 위해 외부 추천·이미지 API를 순차적으로 연동합니다. Python은 스타일 타이틀과 구성 상품 ID를 제공하며, Java 백엔드는 요청 구성, 응답 검증, DB 저장과 이미지 생성 흐름 제어를 담당합니다. Python 내부 구현은 별도 문서에서 다룹니다.

1. AR 상호작용 이력을 Python 서버에 전달합니다.
2. 스타일 타이틀과 Avatar Look 구성 상품 ID를 받습니다.
3. 상품을 DB와 대조하고 추천 순서를 유지합니다.
4. `StyleProfile`, `TodayLook`, `TodayLookItem`을 저장합니다.
5. 기본 성별 아바타와 상품 이미지를 FLUX API에 전달합니다.
6. FLUX 작업 상태를 polling하여 완성 이미지를 다운로드합니다.
7. Python 이미지 서버를 통해 배경을 제거합니다.
8. 이미지를 임시 파일에 기록한 뒤 원자적 이동으로 최종 PNG를 저장합니다.
9. 최종 이미지 URL을 `StyleProfile`에 반영합니다.

외부 응답의 `arSessionId`가 요청과 일치하는지 확인하고 스타일 타이틀, 상품 목록과 상품 ID의 null 여부를 검사합니다. 상품은 일괄 조회 후 응답 ID 순서로 다시 배열하며, 존재하지 않는 상품이 있으면 불완전한 코디가 저장되지 않도록 전체 생성을 중단합니다.

`TodayLookItem.displayOrder`는 응답 순서에 따라 1부터 저장합니다. 따라서 DB 조회 순서와 관계없이 코디 표현 순서를 동일하게 복원할 수 있습니다. 저장 후 `flush()`를 호출하여 이미지 생성 단계 전에 코디 상품이 DB에 반영되도록 했습니다.

FLUX 요청 프롬프트는 Java에서 상품 카테고리와 세부 카테고리에 따라 조립합니다. 작업 제출 응답의 `polling_url`을 주기적으로 조회하고, `Ready`이면 이미지를 다운로드합니다. `Error` 또는 `Failed` 상태는 즉시 실패 처리하고 최대 대기 시간을 넘으면 `504 Gateway Timeout`을 반환합니다.

이미 생성된 결과가 있으면 이를 재사용하여 중복 AI 호출과 비용을 줄입니다. 동시 생성 요청에는 비관적 락을 적용해 같은 세션의 중복 생성을 방지합니다.

### 4.7 My Closet

체험 종료 후 생성된 스타일 프로필을 회원 계정에 연결하고 다시 조회할 수 있습니다.

- 회원별 스타일 프로필 목록
- AI로 생성한 최종 아바타 이미지
- Today Look 구성 상품
- AR에서 실제 피팅한 상품 이력
- 상품별 최종 위시리스트 상태

피팅 이력은 상품 ID 기준으로 중복을 제거하면서 최초 선택 순서를 유지합니다. 위시리스트 상태는 전체 행동을 시간순으로 확인하여 마지막 추가·삭제 행동을 최종 상태로 계산합니다.

중복 제거에는 `LinkedHashMap`을 사용합니다. 상품 ID를 키로 사용하면서 최초 삽입 순서를 보존하기 때문에 같은 상품을 여러 번 피팅해도 한 번만 노출되고 최초 피팅 순서는 유지됩니다. 위시리스트는 `WISHLIST_ADD`, `WISHLIST_REMOVE` 이벤트를 순서대로 덮어써서 최종 상태를 계산하고 Today Look과 피팅 이력에 동일하게 적용합니다.

### 4.8 회원 로그인

로그인 ID로 회원을 조회하고 입력 비밀번호를 SHA-256으로 해시하여 저장값과 비교합니다. `MessageDigest.isEqual`을 사용하며, 아이디가 없거나 비밀번호가 틀린 경우 모두 같은 `401 Unauthorized`를 반환하여 계정 존재 여부가 노출되지 않도록 했습니다.

> 현재는 쇼케이스용 로그인 구현입니다. 운영 환경에서는 bcrypt 또는 Argon2 기반 비밀번호 해싱과 세션/JWT 인증 적용이 필요합니다.

## 5. 주요 데이터 모델

| 도메인 | 엔티티 | 역할 |
| --- | --- | --- |
| 방문 | `CustomerSession` | 고객 방문 생명주기 관리 |
| 방문 | `StoreZone`, `ZoneCategory` | 매장 층과 상품 카테고리 연결 |
| 방문 | `ZoneInteraction` | 층·카테고리별 체류 이력 |
| AR | `ArSession` | 방문, 회원, 성별, 피팅 경험 통합 |
| AR | `ArInteraction` | 상품 선택 및 위시리스트 행동 |
| AR | `ArMessageHistory` | 상황 기반 메시지 노출 이력 |
| 상품 | `Product`, `Category` | 추천 및 피팅 대상 상품 |
| 회원 | `Member`, `MemberWishlist` | 회원 정보 및 선호 상품 |
| 스타일 | `StyleProfile` | 체험 결과로 생성된 스타일 정체성 |
| 스타일 | `TodayLook`, `TodayLookItem` | 최종 코디와 상품 순서 |

주요 관계는 다음과 같습니다.

- `ArSession N:1 CustomerSession`: 한 방문에서 여러 AR 체험으로 확장 가능
- `ArSession N:1 Member`: 한 회원의 여러 체험 이력 보관
- `ArInteraction N:1 ArSession`: 세션별 행동 로그 축적
- `ArInteraction N:1 Product`: 각 행동의 대상 상품 연결
- `StyleProfile N:1 ArSession`: 세션에서 생성된 스타일 결과 보관
- `TodayLookItem N:1 TodayLook`: 코디 상품과 노출 순서 저장

## 6. 안정성 및 데이터 정합성

### 트랜잭션 관리

변경 로직은 `@Transactional`, 조회 로직은 `@Transactional(readOnly = true)`로 구분했습니다. 외부 호출은 필요한 경우 DB 커밋 이후 실행하여 내부 저장 성공 여부와 외부 시스템 장애를 분리합니다.

### 동시성 제어

Avatar Look 중복 생성과 AR 메시지 중복 평가가 중요한 구간에서 `findByIdForUpdate` 기반 비관적 락을 적용했습니다.

### 외부 API 장애 처리

추천 서버와 이미지 서버별 연결·읽기 timeout을 설정했습니다. 빈 응답, 잘못된 상품 ID, 외부 서버 오류, 이미지 생성 timeout을 검증하고 `502 Bad Gateway`, `504 Gateway Timeout` 등 적절한 HTTP 상태로 변환합니다.

### 이미지 저장 안정성

생성 이미지는 임시 파일에 기록한 뒤 `ATOMIC_MOVE`로 최종 경로에 교체합니다. 원자적 이동을 지원하지 않는 파일 시스템에서는 일반 교체 방식으로 fallback합니다. 경로 정규화와 상위 디렉터리 검증을 통해 의도하지 않은 위치로의 파일 저장도 방지합니다.

### 외부 응답 검증

추천 결과의 세션 ID, 상품 목록, 스타일 타이틀을 검사하고 상품을 내부 DB와 다시 매핑합니다. 외부 서비스의 불완전한 응답이 영속화되거나 클라이언트로 전달되는 것을 방지합니다.

### 공개 이미지 URL 처리

DB에는 `/images/...` 상대 경로를 저장하지만 외부 이미지 API에는 접근 가능한 절대 URL이 필요합니다. `ImageUrlResolver`는 기존 HTTP(S) URL은 유지하고 상대 경로에 `PUBLIC_BASE_URL`을 결합합니다. 공개 주소가 설정되지 않았다면 즉시 실패시켜 접근 불가능한 URL이 외부 API로 전달되지 않도록 했습니다.

### HTTP 예외 정책

| 상태 | 적용 상황 |
| --- | --- |
| `400 Bad Request` | 잘못된 시간 범위, 필수 추천 데이터 누락 |
| `401 Unauthorized` | 로그인 정보 불일치 |
| `404 Not Found` | 세션, 회원, 상품 등 리소스 미존재 |
| `409 Conflict` | 세션 중복 종료 또는 다른 대상과 재연결 |
| `502 Bad Gateway` | 외부 이미지 API 오류 또는 잘못된 응답 |
| `504 Gateway Timeout` | 이미지 생성 최대 대기 시간 초과 |

## 7. 배포 구성

멀티 스테이지 Dockerfile을 사용합니다. 빌드 단계에서는 JDK 17로 실행 JAR을 만들고 실행 단계에서는 JRE 17 이미지만 사용합니다.

Docker Compose는 Spring Boot와 MySQL 8을 구성합니다. MySQL health check 성공 후 애플리케이션이 시작되며, DB 데이터는 Docker volume에 영속화합니다. DB 접속 정보, Python 서버 주소, FLUX API Key, API timeout, polling 주기, 이미지 저장 경로 등은 환경 변수로 분리했습니다.
